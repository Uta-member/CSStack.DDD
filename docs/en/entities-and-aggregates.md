# Entities and aggregates

## Entities

An entity is an object defined by its identity rather than its attributes. A member who changes their email address is still the same member.

| Type | Purpose |
|---|---|
| `IEntity<TSelf, TId>` | An entity. Requires `Id` and `IEquatable<TSelf>`. Derive from `Entity<TSelf, TId>` to also get the `==` and `!=` operators. |
| `Entity<TSelf, TId>` | A base class that implements equality by identifier. |

### Equality by identifier

`Entity<TSelf, TId>` compares entities by `Id`. `Equals(object)` and `GetHashCode()` are **sealed**, so derived classes cannot change how identity is compared.

```csharp
public sealed class Member : Entity<Member, MemberId>
{
	public override MemberId Id { get; }
	// ...
}
```

- Two entities of the same type with the same `Id` are equal, even if their other attributes differ. This is the meaning of identity.
- Entities of different types are never equal, even if their identifiers have the same underlying value.
- The type check uses `is TSelf` rather than `GetType()`, so it also works with proxy classes generated by ORMs.

To compare the contents of two entities (for example, in tests), compare their properties explicitly or use an assertion library that compares objects structurally.

### Assign the identifier on creation

Generate the identifier in the domain when the entity is created, for example with `MemberId.New()`.

If the database generates the identifier, all new entities share the same default value (such as `0`) until they are saved, so they are considered equal. The hash code also changes after saving, which breaks `HashSet` and `Dictionary`.

## Aggregate roots

An aggregate is a cluster of entities and value objects that is kept consistent as a unit. The aggregate root is the entity through which all changes to the aggregate are made.

| Type | Purpose |
|---|---|
| `IAggregateRoot<TSelf, TId>` | An aggregate root. Also an `IDomainEventSource`. |
| `AggregateRoot<TSelf, TId>` | A base class that records domain events. Derives from `Entity<TSelf, TId>`. |

Repositories are defined per aggregate root only. Entities inside an aggregate are not loaded or saved on their own.

## Lifecycle: creation and reconstruction

The validity of the state is owned by the lifecycle of the entity. Provide separate factory methods for creating a new entity and for reconstructing an existing one.

```csharp
public sealed class Member : AggregateRoot<Member, MemberId>
{
	public override MemberId Id { get; }
	public MemberName Name { get; private set; }
	public Email Email { get; private set; }

	private Member(MemberId id, MemberName name, Email email)
	{
		Id = id;
		Name = name;
		Email = email;
	}

	// Creation: validates the input, applies business policies and raises an event
	public static Member Register(MemberName name, Email email, DateTimeOffset occurredAt)
	{
		List<ValidationError> errors =
		[
			.. name.Validate().Under(nameof(Name)),
			.. email.Validate().Under(nameof(Email)),
		];
		if (name.Value.Length > 20)
		{
			errors.Add(new TooLong(20, name.Value.Length) { Path = nameof(Name) }); // a policy for registration
		}
		errors.ThrowIfInvalid();

		var member = new Member(MemberId.New(), name, email);
		member.AddDomainEvent(new MemberRegistered(Guid.NewGuid(), occurredAt, member.Id, email));
		return member;
	}

	// Reconstruction: restores past state, so no validation and no events
	public static Member Reconstruct(MemberId id, MemberName name, Email email)
	{
		return new Member(id, name, email);
	}
}
```

The toolkit does not define `Create` or `Reconstruct` in an interface, because their parameters differ for every entity. Treat them as a convention.

## Operations

State changes are made through operations named after the intent of the business, not through setters.

```csharp
public void ChangeEmail(Email email, DateTimeOffset occurredAt)
{
	email.Validate().Under(nameof(Email)).ThrowIfInvalid(); // the gate
	Email = email;
	AddDomainEvent(new MemberEmailChanged(Guid.NewGuid(), occurredAt, Id, email));
}
```

- **Prefer intent over overwriting.** An operation such as `UpdateMember(name, email, address, ...)` that overwrites every field can silently discard changes made by others. Operations such as `ChangeEmail` touch only what they mean to change.
- **Business rules that are not about the input** (for example, "a withdrawn member cannot change the email address") are also checked in the operation. Throw your own exception for them.

## Who performed an operation

Distinguish between two kinds of "who":

| Kind | Examples | Where it belongs |
|---|---|---|
| Who has a business meaning | Approver, requester, assignee | The state of the aggregate. Pass it as an argument of the operation. |
| Who is recorded for auditing | Last modified by, created by | The infrastructure. Record it on commit from the execution context. |

```csharp
public void Approve(UserId approver, DateTimeOffset occurredAt)
{
	if (approver == RequestedBy)
	{
		throw new ApprovalRuleException("The requester cannot approve their own request.");
	}
	ApprovedBy = approver;
	AddDomainEvent(new OrderApproved(Guid.NewGuid(), occurredAt, Id, approver));
}
```

Do not add audit columns such as `UpdatedBy` or `UpdatedAt` to the aggregate.

## Deletion with a business meaning

If "deleting" has a meaning in the business, such as withdrawal or cancellation, model it as a state transition and save it like any other change.

```csharp
public void Withdraw()
{
	if (IsWithdrawn)
	{
		throw new MembershipRuleException("The member has already withdrawn.");
	}
	IsWithdrawn = true;
}
```

Use `IDeletableRepository` only for aggregates that actually cease to exist. See [Repositories and the unit of work](repositories-and-unit-of-work.md).

Do not filter out withdrawn aggregates automatically in the infrastructure (for example, with a global query filter). The aggregate itself should decide what it can do in its current state.
