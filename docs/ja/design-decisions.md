# 設計判断

このページでは、CSStack.DDD がなぜこのように設計されているのかを説明します。

## 値オブジェクトはコンストラクターで検証しない

**判断：** コンストラクターは、型が存在するための最低限の条件（null でないことなど）だけを確認します。ルールは `Validate()` が報告します。

**理由：** 値が妥当でなければならないかどうかは、エンティティのライフサイクルによって決まります。エンティティの生成時や変更時には値を検証する必要がありますが、永続化層から再構築するときには必要ありません。コンストラクターが不正な値を拒否すると、古いルールのもとで保存されたデータを読み込めなくなります。また、不正な値を 1 つ含む集約は、その値を修正するためであっても読み込めなくなります。

**トレードオフ：** 型だけでは妥当性は保証されません。妥当性は、すべての書き込みがドメインの操作を経由することによって保証されます。

## ライフサイクルはエンティティが持つ

**判断：** エンティティは、生成用（検証とイベント発行を伴う）と再構築用（どちらも伴わない）に別々のファクトリを提供します。値オブジェクトのコンストラクターは 1 つだけです。

**理由：** 生成と再構築は、値ではなくエンティティの生涯における異なる時点です。値オブジェクトに両方のファクトリを持たせると、同じ区別があらゆる型に散らばってしまいます。

## バリデーションはエラーを返し、操作は例外をスローする

**判断：** `IValidatable.Validate()` はエラーのリストを返します。エンティティの操作は `DomainValidationException` をスローします。

**理由：** 診断ではすべてのエラーを収集する必要がありますが、例外ではそれができません。強制は無視できないものでなければなりませんが、戻り値ではそれを保証できません。どちらか一方の仕組みだけでは、両方の要件を満たせません。強制はエンティティの操作でのみ行われるため、強制の漏れは操作の振る舞いのバグとなり、その操作のテストで見つけることができます。

## ドメインの例外は共通の基底クラスを持つ

**判断：** `DomainValidationException` は抽象クラス `DomainException` から派生します。「申請者は自分の申請を承認できない」のような入力に関するものではないビジネスルールの例外はアプリケーションが定義し、これも `DomainException` から派生させます。`ConcurrencyConflictException` は派生しません。

**理由：** 上位の層は、ドメインが拒否したすべての操作を 1 か所で処理する必要があります（たとえば HTTP 400 や 422 に変換する）。共通の基底がなければ、例外を追加するたびにその処理にも追加しなければなりません。入力に関するものではないビジネスルールは、指し示す入力がないので、バリデーションエラーとしては報告しません。`DomainException` を抽象クラスにしているのは、それぞれのルールをメッセージではなく専用の型で表すためです。同時実行の競合は、ドメインのルールによる拒否ではなくインフラストラクチャが検出するものなので、`ConcurrencyConflictException` はアプリケーション層に置いています。

## エラーはコードではなく型付きのレコードにする

**判断：** エラーの種類ごとに、`ValidationError` から派生した型付きのプロパティを持つ型を用意します。

**理由：** 文字列コードと `object` 型の引数を入れた辞書の組み合わせは、正しく使うのが困難です。型付きのレコードであれば、パターンマッチングで処理でき、テストでは値で比較でき、型の識別子付きでシリアル化できます。例外のリストも検討しましたが、例外には、診断には不要なスタックトレース、メッセージ、変更可能なデータが含まれます。

## 数値の組み込みエラーはジェネリックにしない

**判断：** 数値が境界の外にあることは、`BelowMinimum(decimal Minimum, decimal Actual)` と `AboveMaximum(decimal Maximum, decimal Actual)` で報告します。ジェネリックな範囲のエラーは提供しません。

**理由：** `OutOfRange<T>` のようなジェネリックなエラーは、`T` が分からないとパターンマッチできず、シリアライズでも閉じた型ごとに登録が必要になります。`decimal` は整数も小数も正確に表せます。両方の境界が必須の範囲では「1 以上」のような片側だけのルールを表せないため、境界ごとに別のエラーにしています。長さについての `TooLong` と `TooShort` と混同しないよう、名前も分けています。日付などほかの種類の値は、ドメイン固有のエラーに任せます。

## エラーはパスを持つ

**判断：** `ValidationError.Path` はドット区切りの文字列で、各階層が `Under` を使って組み立てます。

**理由：** 値オブジェクトは、自分がどのエンティティのどのプロパティに含まれているかを知りません。各階層は自分自身のメンバー名だけを追加します。配列ではなく文字列を使うのは、レコードが値による等価性を保てるようにするため、またパスを ASP.NET Core で使われるキーと一致させるためです。

## エンティティの等価性は基底クラスで強制する

**判断：** `Entity<TSelf, TId>` は識別子による等価性を実装し、`Equals` と `GetHashCode` を sealed にしています。

**理由：** インターフェースでは、等価性を実装することは要求できても、どのように実装するかまでは要求できません。エンティティが識別子で比較されることを保証できるのは、基底クラスだけです。

## ドメインイベントはコミット時に取り出す

**判断：** 集約はイベントを記録し、インフラストラクチャがコミット時に非ジェネリックな `IDomainEventSource` を通じてそれを取り出します。

**理由：** すぐに配信すると、後でロールバックされる変更を公開してしまうおそれがあります。コミット時に取り出せば、同じトランザクション内でイベントを Outbox に書き込めます。取得とクリアを 1 回の呼び出しで行うことで、二重配信を防ぎます。

## イベントのハンドラーと配信の仕組みは提供しない

**判断：** ツールキットが提供するのは、イベントの記録と回収（`IDomainEvent`、`IDomainEventSource`）までです。ハンドラーのインターフェース、ディスパッチャー、Outbox、リトライ、パイプラインは提供しません。

**理由：** ハンドラーをどの単位で解決し、どのトランザクションで、どう再試行して呼び出すかは、アプリケーションの構成によって変わります。スコープをイベントごとに作るのかハンドラーごとに作るのか、メッセージブローカーを使うのか、などです。特定の構成を前提にしたディスパッチャーを提供すると、それに合わないアプリケーションでは使えず、誤った構成に誘導するおそれもあります。また、MediatR、Wolverine、MassTransit などは独自のハンドラーのインターフェースを持っているため、ツールキットのインターフェースと重複します。

**トレードオフ：** イベントの型からハンドラーを解決して呼び出す仕組みは、各アプリケーションで用意するか、ライブラリを選んで使う必要があります。

## イベントへの反応は、既定では元の変更とは別のトランザクションで行う

**判断：** ドキュメントでは、Unit of Work が集約と同じトランザクションでイベントを Outbox に書き込み、Outbox の発行プロセスが別のトランザクションでイベントに反応させる構成を、既定として推奨します。コミット前に同じトランザクション内で反応させるのは、業務が即時の整合性を必要とする場合に限ります。

**理由：** 他の集約の更新を同じトランザクションで行うと、その失敗によって、成功していた元の変更までロールバックされます。これは、他の集約をドメインイベントで結果整合的に更新するという指針と矛盾します。Outbox を経由すれば、元の変更とイベントの記録は原子的に行われ、反応の失敗はリトライで回復できます。

**トレードオフ：** 反応による変更は、元の変更より遅れて反映されます。イベントは at-least-once で届くため、反応は冪等に実装する必要があります。

## リポジトリは `Add` と `Update` ではなく `Save` を持つ

**判断：** `IRepository` は `FindAsync` と `Save` を持ちます。挿入か更新かは実装が決めます。

**理由：** `Add` と `Update` は、データベースの関心事（INSERT か UPDATE か）を呼び出し側に露出させます。`Add` と `Remove` だけを持つコレクション風のリポジトリには変更追跡が必要となり、ツールキットが EF Core などの ORM に縛られてしまいます。`Save` であれば、どのデータアクセス技術でも機能します。

## 削除はオプション

**判断：** `Delete` は別のインターフェース `IDeletableRepository` に置いています。

**理由：** 多くの集約は物理的に削除されることがありません。退会のように削除が業務上の意味を持つ場合、それは集約の状態遷移です。

## ドメインは `Version` を持たない

**判断：** 集約ルートに `Version` プロパティを持たせません。同時実行トークンはインフラストラクチャで保持します。

**理由：** バージョンは永続化の関心事です。インフラストラクチャは、読み込んだ各集約のトークンを追跡し、ドメインに露出させることなく競合を検出できます。

## トランザクションは Unit of Work が管理する

**判断：** リポジトリはトランザクションをパラメーターとして受け取りません。アプリケーション層が `IUnitOfWork` を通じてコミットします。

**理由：** トランザクションを引数で渡すと、ドメインのインターフェースにインフラストラクチャの型が入り込み、すべてのメソッドにパラメーターが増えます。さらに、渡し忘れるとトランザクションの外で気づかないうちに実行されてしまいます。また、Unit of Work は、変更されたすべての集約からドメインイベントを回収する場所としても自然です。

## ツールキットが提供しないもの

| 提供しないもの | 理由 |
|---|---|
| `IDomainService` | 要求すべきメンバーがないため。命名規約とアーキテクチャテストを使用してください。 |
| 現在のユーザーの実行コンテキスト | インフラストラクチャの関心事であるため。 |
| `Result` 型 | このツールキットは強制に例外を使用するため。 |
| コマンドハンドラーやメディエーター | アプリケーションのアーキテクチャ上の選択であり、DDD の一部ではないため。 |
| ドメインイベントのハンドラーとディスパッチャー | 解決と呼び出しの方法がアプリケーションの構成によって変わるため。[イベントのハンドラーと配信の仕組みは提供しない](#イベントのハンドラーと配信の仕組みは提供しない) を参照してください。 |
