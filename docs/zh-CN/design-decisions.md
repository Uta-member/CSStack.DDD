# 设计决策

本页说明 CSStack.DDD 为何采用现在的设计。

## 值对象不在构造函数中校验

**决策：** 构造函数只检查该类型得以存在的最低条件（例如非 null）。规则由 `Validate()` 报告。

**理由：** 一个值是否必须有效，取决于实体的生命周期。实体在创建或变更时必须校验值，但从持久化数据重建时则不应校验。如果构造函数拒绝无效值，按旧规则保存的数据将无法加载；只要聚合中有一个无效值，就连为了修正该值而加载它都做不到。

**代价：** 仅靠类型本身无法保证有效性。有效性的保证来自于所有写入都必须经过领域中的某个操作。

## 生命周期由实体负责

**决策：** 实体分别为创建（含校验和事件）与重建（两者都不含）提供不同的工厂方法。值对象只有一个构造函数。

**理由：** 创建和重建是实体生命中的不同时刻，而不是值的。如果在值对象上也提供这两种工厂方法，同样的区分就会扩散到每一个类型中。

## 校验返回错误，操作抛出异常

**决策：** `IValidatable.Validate()` 返回错误列表。实体的操作抛出 `DomainValidationException`。

**理由：** 诊断需要收集所有错误，而异常做不到这一点。强制执行需要做到无法被忽略，而返回值无法保证这一点。任何单一机制都无法同时满足这两种需求。由于强制执行只发生在实体的操作中，遗漏强制执行就是操作行为上的缺陷，可以通过该操作的测试发现。

## 领域的异常拥有共同的基类

**决策：** `DomainValidationException` 派生自抽象类 `DomainException`。与输入无关的业务规则（例如“申请人不能批准自己的申请”）的异常由应用程序定义，同样派生自 `DomainException`。`ConcurrencyConflictException` 不派生自它。

**理由：** 上层需要在一处统一处理所有被领域拒绝的操作（例如转换为 HTTP 400 或 422）。如果没有共同的基类，每新增一个异常，都必须同时添加到这段处理中。与输入无关的业务规则没有可指向的输入，因此不作为校验错误报告。`DomainException` 之所以是抽象类，是为了让每条规则由各自的类型而不是消息来表示。并发冲突不是被领域规则拒绝，而是由基础设施层检测到的，因此 `ConcurrencyConflictException` 位于应用层。

## 错误是强类型的 record，而不是代码

**决策：** 每种错误都是派生自 `ValidationError` 的类型，并带有强类型属性。

**理由：** 字符串代码加上 `object` 参数字典的方式很难被正确使用。强类型 record 可以用模式匹配处理，可以在测试中按值比较，也可以借助类型鉴别器进行序列化。我们也考虑过使用异常列表，但异常带有堆栈跟踪、消息和可变数据，而这些都是诊断所不需要的。

## 数值的内置错误不是泛型

**决策：** 数值超出边界时，用 `BelowMinimum(decimal Minimum, decimal Actual)` 和 `AboveMaximum(decimal Maximum, decimal Actual)` 报告。不提供泛型的范围错误。

**原因：** 像 `OutOfRange<T>` 这样的泛型错误，在不知道 `T` 的情况下无法进行模式匹配，序列化时也需要为每个封闭类型分别注册。`decimal` 可以精确表示整数和小数。两个边界都必需的范围无法表达“1 以上”这样只有一侧的规则，因此每个边界都是独立的错误。为避免与针对长度的 `TooLong` 和 `TooShort` 混淆，名称也有所区分。日期等其他种类的值交给领域特有的错误。

## 错误带有路径

**决策：** `ValidationError.Path` 是以点分隔的字符串，由每一层通过 `Under` 构建。

**理由：** 值对象并不知道自己位于哪个实体的哪个属性中。每一层只添加自己的成员名。之所以使用字符串而不是数组，是为了让 record 保持按值相等，并使路径与 ASP.NET Core 使用的键一致。

## 实体的相等性由基类强制保证

**决策：** `Entity<TSelf, TId>` 实现基于标识符的相等性，并将 `Equals` 和 `GetHashCode` 设为 sealed。

**理由：** 接口可以要求实现相等性，却无法规定如何实现。只有基类才能保证实体按标识符进行比较。

## 领域事件在提交时取出

**决策：** 聚合负责记录事件，基础设施层在提交时通过非泛型的 `IDomainEventSource` 取出这些事件。

**理由：** 立即分发可能会发布之后被回滚的变更。在提交时取出事件，就可以在同一事务中将其写入发件箱。在一次调用中完成获取与清空，可以防止重复分发。

## 不提供事件处理器和分发机制

**决策：** 工具包只提供事件的记录与收集（`IDomainEvent`、`IDomainEventSource`）。不提供处理器接口、分发器、发件箱、重试或管道。

**理由：** 如何解析处理器、在哪个事务中运行、如何重试，取决于应用程序的构成：例如是按事件还是按处理器创建作用域，是否使用消息代理等。如果提供以某种特定构成为前提的分发器，不符合该构成的应用程序就无法使用，还可能被引向错误的构成。此外，MediatR、Wolverine、MassTransit 等库都有自己的处理器接口，工具包的接口会与之重复。

**代价：** 根据事件类型解析并调用处理器的机制，需要由各应用程序自行准备，或选用相应的库。

## 默认情况下，在与原始变更分开的事务中对事件作出响应

**决策：** 文档推荐的默认做法是：工作单元在与聚合相同的事务中将事件写入发件箱，由发件箱发布进程在另一个事务中对事件作出响应。只有当业务要求立即一致时，才在提交前于同一事务中作出响应。

**理由：** 如果在同一事务中更新其他聚合，其失败会导致原本已成功的原始变更也被回滚。这与“通过领域事件以最终一致性更新其他聚合”的指导原则相矛盾。借助发件箱，原始变更与事件记录是原子的，响应的失败可以通过重试恢复。

**代价：** 响应产生的变更会晚于原始变更生效。事件至少会投递一次，因此响应必须实现为幂等的。

## 仓储提供 `Save`，而不是 `Add` 和 `Update`

**决策：** `IRepository` 提供 `FindAsync` 和 `Save`。插入还是更新由实现决定。

**理由：** `Add` 和 `Update` 会把数据库层面的关注点（INSERT 还是 UPDATE）暴露给调用方。而只有 `Add` 和 `Remove` 的集合式仓储需要变更跟踪，这会把工具包与 EF Core 之类的 ORM 绑定在一起。`Save` 则适用于任何数据访问技术。

## 删除是可选的

**决策：** `Delete` 放在单独的接口 `IDeletableRepository` 中。

**理由：** 许多聚合从不会被物理删除。当删除具有业务含义（例如退会）时，它是聚合的一种状态迁移。

## 领域中没有 `Version`

**决策：** 聚合根上没有 `Version` 属性。并发令牌保存在基础设施层中。

**理由：** 版本是持久化层面的关注点。基础设施层可以跟踪每个已加载聚合的令牌并检测冲突，而无需将其暴露给领域。

## 事务由工作单元管理

**决策：** 仓储不接收事务参数。应用层通过 `IUnitOfWork` 提交。

**理由：** 传递事务会把基础设施层的类型带入领域接口，并给每个方法增加一个参数；而一旦忘记传递，代码就会悄无声息地在事务之外执行。此外，工作单元也天然是从每个被修改的聚合中收集领域事件的地方。

## 本工具包不提供的内容

| 不提供 | 原因 |
|---|---|
| `IDomainService` | 没有需要强制实现的成员。请使用命名约定和架构测试。 |
| 当前用户的执行上下文 | 这是基础设施层的关注点。 |
| `Result` 类型 | 本工具包使用异常来进行强制。 |
| 命令处理器或中介者（mediator） | 它们是应用程序的架构选择，而不是 DDD 的一部分。 |
| 领域事件处理器与分发器 | 其解析和调用方式取决于应用程序的构成。请参阅[不提供事件处理器和分发机制](#不提供事件处理器和分发机制)。 |
